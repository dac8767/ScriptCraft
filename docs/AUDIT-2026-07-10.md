# ScriptCraft Security & IP Audit — 2026-07-10 (v0.54)

Scope: full repo scan — frontend, backend, collab server, Tauri shell, bundled
assets, dependency manifests, and git-tracked files. Severity reflects a
public free-and-open-source release; several items are harmless while the app
runs purely on localhost.

---

## Part 1 — Security

### S1. Path traversal via `project_id` / `script_id` path params — HIGH
Every file-touching service builds paths as `get_projects_dir() / project_id`
(project_service.py:34/83, script_service, asset_service `_assets_dir`) with
**no validation** of the id. Route params are raw `str`; an encoded segment
(`..%2F..%2Fetc`) or a bare `..` id reaches the join and escapes the projects
root — confirmed by simulation (`Path('/data/projects') / '../../etc/passwd'`
resolves to `/etc/passwd`). On a hosted deployment this is read/write outside
the data directory (e.g. PUT script content to an arbitrary path). All real
ids are uuid4.
**Fix:** validate ids with `re.fullmatch(r'[0-9a-f-]{36}', id)` at the route
layer (or a shared `_project_dir()` that does `resolved.is_relative_to(root)`)
and 404 on failure. One helper, used everywhere.

### S2. Asset uploads keep the user's file extension — MEDIUM
`asset_service.save` stores `f"{uuid4()}{ext}"` where `ext` comes from the
uploaded filename, unvalidated. A `.html`/`.svg` upload later served from the
same origin executes script in the app's origin (stored XSS). Size is capped;
type is not.
**Fix:** whitelist extensions (images/pdf/audio/video the Asset Manager
actually supports), or serve assets with `Content-Disposition: attachment`
and `X-Content-Type-Options: nosniff`.

### S3. Vulnerable npm dependencies — MEDIUM (fixes available)
`npm audit --omit=dev`: 6 advisories — dompurify ≤3.4.10 (moderate),
linkify-it (high), markdown-it ≤14.1.1 (moderate, ReDoS), react-router
7.0.0–7.15.0 (high), ws (high), one more transitive. All have non-breaking
fixes: run `npm audit fix` in `frontend/` and re-run the test suite. Backend
Python deps were not vulnerability-scanned in this pass — run `pip-audit` as
a follow-up.

### S4. CORS: private-LAN origin regex with `allow_credentials=True` — LOW
`main.py` allows `localhost`, `127.0.0.1`, and RFC-1918 ranges by regex with
credentials. Fine for the local/dev topology; a *hosted* deployment must set
`CORS_ORIGINS` to the real origin and should drop the LAN regex, otherwise
any service on a user's LAN IP can make credentialed calls.

### S5. Tokens in `localStorage` — LOW / accepted trade-off
Auth and OAuth PKCE tokens persist in `localStorage`
(settingsStore.ts:138, oauthPkce.ts:90). Standard for SPAs but XSS-readable —
which is why S2/S6 matter. No `client_secret` exists anywhere in the frontend
(PKCE only) ✓. No token/secret logging found beyond an informational expiry
message ✓.

### S6. `dangerouslySetInnerHTML` for the Index Cards drag ghost — LOW
IndexCards.tsx:777 re-injects `dragCardHtml` captured from the app's own
rendered DOM. The content was React-escaped at first render, so risk is low,
but `cloneNode(true)` on the card element would remove the innerHTML string
round-trip entirely. All other rich rendering paths use DOMPurify ✓.

### S7. Developer-side hygiene — ACTION FOR DEREK
- **Rotate the GitHub personal access token** that was pasted into the chat
  session used to drive this work. It is not in any tracked file or commit
  (verified: no secrets in the working tree or in `git log --all` file
  history), but it exists in chat logs; treat it as exposed and reissue.
- Only `.env.example` files are tracked ✓; keep real `.env` files ignored.
- The delivery zips at the repo root contain source only — no secrets ✓.

### S8. Posture that is already good — INFO
JWT verification **fails closed** when `COLLAB_JWT_SECRET` is unset (401s,
loud log) ✓. Collab server refuses to start in production without
`JWT_SECRET` and uses a random per-boot secret in dev ✓. Static file serving
guards against traversal (`STATIC_DIR in resolved.parents`) ✓. No raw SQL
(no injection surface found) ✓. No `eval`/`new Function` ✓.

## Part 2 — Copyright / Trademark

### T1. ScriptCraft brand assets are still in the repo — HIGH for release
`images/` ships Proteus Technologies' brand art: `OpenDraft-1024x1024.png`,
`OpenDraft-intro.mp4`, `OpenDraft.png`, `OpenDraft_icon.png`, iOS/Android
icon sets, feature graphics — and `src-tauri/icons/` plus
`frontend/public/splash-logo.png` / `favicon` are of the same lineage. The
MIT license covers the **code**; logos and brand identity are trademark
territory and imply affiliation. Before public release: replace every icon,
splash, favicon, store graphic, and the intro video with ScriptCraft's own art,
or obtain written permission.

### T2. Upstream license obligations — COMPLIANT, keep it that way
Upstream is MIT, "Copyright (c) 2026 Proteus Technologies". MIT requires the
copyright notice and license text to remain in all copies — keep `LICENSE`
intact (add a second copyright line for ScriptCraft contributions rather than
replacing theirs). The About-dialog attribution added in v0.50 is good
practice on top.

### T3. "Final Draft" references — LOW, nominative use
The name appears only as compatibility wording: the import menu ("Final
Draft / Fountain / ScriptCraft…"), `.fdx` parser internals, and the font-family
fallback string "Courier Final Draft" (referenced by name for imported
documents that specify it — the font file itself is **not** shipped;
verified `public/fonts` contains only Courier Prime). Nominative use for
file-format compatibility is the same pattern as "Microsoft Word (.docx)".
Keep it factual: no Final Draft logos, no "works just like Final Draft"
marketing copy, and consider phrasing the menu item "Final Draft (.fdx)".

### T4. The name "ScriptCraft" — MEDIUM, do a clearance check
"Draft" is descriptive and "ScriptCraft" ≠ "Final Draft", but the products are
direct substitutes in the same market, which is exactly where trademark
similarity arguments live. Before the public launch, run a basic clearance:
USPTO TESS search for FreeDraft/near-marks in software, plus an app-store and
domain sweep for existing "ScriptCraft" software. Cheap now, expensive later.

### T5. Hunspell dictionaries lack their license files — MEDIUM
`frontend/public/dictionaries/en_US.{dic,aff}` and the `dictionaries-extra/`
locales ship with **no license/readme text** alongside. Hunspell en_US is
SCOWL-derived (BSD-style with required notices); other locales vary
(LGPL/MPL/GPL depending on source). Redistribution requires including each
dictionary's license file. Action: fetch the upstream license text for every
bundled locale and drop it next to the files; drop any locale whose license
is copyleft in a way you don't want to carry.

### T6. Courier Prime — COMPLIANT with one addition
OFL-licensed ✓, but the OFL requires the license text to accompany the font
files. Add `OFL.txt` to `frontend/public/fonts/`.

### T7. Dependency licenses — CLEAR
Manifest scan: React, TipTap/ProseMirror, Yjs, Hocuspocus, Vite, Zustand,
React Router, Recharts, dnd kit, react-icons (Font Awesome Free — CC BY 4.0
icons, attribution satisfied by the license file), jsPDF, docx, JSZip,
DOMPurify, Harper (Apache-2.0), Typo.js, retext/unified — all permissive.
FastAPI/uvicorn/pydantic permissive; **dulwich is Apache-2.0/GPLv2+
dual-licensed — elect Apache-2.0** in your notices. No copyleft obligation
forces a license change for the app. Recommend generating a THIRD-PARTY
notices file (`license-checker` / `pip-licenses`) at release time.

### T8. Store badges — INFO
`images/badges/` (App Store / Google Play badges) are fine to use only per
Apple/Google's badge guidelines and only when linking to actual listings.
